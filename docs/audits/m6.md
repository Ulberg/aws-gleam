# M6 audit — typed bodies, errors, decoders

Scope: M6.1 through M6.7 plus M6.8 (client wiring) and M6.9 (real-model
codegen for DynamoDB + S3). Treat as the audit of the surface produced
in this branch (`plan/m5-codegen`).

**Update (2026-05-18):** the v0.2 candidates "Codegen-driven additional
services", "Paginators", and "Waiters" all landed in this PR.

* All ~409 mainline-protocol services (awsJson1_0 / awsJson1_1 /
  restJson1 / restXml) generate, format, and compile under
  `./scripts/test.sh` (which exports `ERL_FLAGS="+t 4194304"` to
  cover the extra few million atoms the generated source
  introduces). `awsQuery` / `ec2Query` / `rpcv2Cbor` services are
  still skipped until their body codecs land.
* The codegen emits a `paginate_<op>(client, input, acc, reducer)`
  wrapper for every operation carrying `smithy.api#paginated`.
  Built on the new `aws/pagination.fold` runtime helper, parametric
  over cursor type (so DynamoDB's `LastEvaluatedKey` —
  `Dict(String, AttributeValue)` — and a plain `String`
  `NextToken` flow through the same helper).
* `test/service_smoke_test.gleam` adds three per-protocol
  smoke tests (SQS / CloudWatch Logs / EKS) covering the
  `<service>.new` → SigV4 → embedded rule set → host path on
  protocols the existing DynamoDB / S3 endpoint tests don't reach.
  `test/paginator_smoke_test.gleam` exercises the generated
  `DynamoDB.paginate_list_tables` end-to-end (2-page fold +
  cursor threading against a mock transport).
* `aws/waiter.wait(step, max_attempts, min_delay_ms, max_delay_ms)`
  drives a polling closure with exponential backoff capped at
  `max_delay_ms`. The codegen emits one `wait_until_<waiter>`
  function per `smithy.waiters#waitable` waiter; acceptors with
  `success` / `errorType` matchers translate to typed-variant
  pattern matches (with a `<Op>ErrorUnknown(error_type:
  "<wire>", ..)` fall-through for error types the op didn't
  explicitly declare). JMESPath matchers (`output`,
  `inputOutput`, `outputCount`, `errorContains`) are dropped at
  trait-parse time — waiters carrying any of them aren't emitted.
  `test/waiter_smoke_test.gleam` exercises the generated
  `S3.wait_until_bucket_exists` (settles on first 200).
* The pass / fail counts in §"Wire-format verification" remain
  authoritative — they come from the protocol-test corpus, which
  is decoupled from the service-model count.

## What the user sees

After this milestone series, a caller has a typed Gleam API for two
real AWS services:

```
let client = dynamodb.new(provider: provider, region: "us-east-1")
case dynamodb.list_tables(client, dynamodb.ListTablesInput(...)) {
  Ok(out) -> ...
  Error(dynamodb.ListTablesErrorInternalServerError(value: e)) -> ...
  Error(dynamodb.ListTablesErrorTransport(reason: r)) -> ...
  Error(dynamodb.ListTablesErrorUnknown(...)) -> ...
}
```

Same shape for `aws/services/s3.gleam` — 77 operations, typed input,
typed output, typed error enum, XML body encoding, XML response
decoding.

## Generator architecture

Three layers — same as smithy-rs:

1. **Runtime** (`src/aws/internal/...`) — hand-written, ~2 kLOC.
   SigV4, credentials chain, retry, http_send, codecs (`json_float`,
   `xml`, `xml_decode`, `rest`), shared `runtime.invoke`.

2. **Generator** (`codegen/src/codegen/...`) — hand-written, ~4 kLOC.
   `types.gleam` resolves Smithy shapes to a thin `Resolved` IR;
   `awsjson.gleam`, `restjson.gleam`, `restxml.gleam`,
   `awsquery.gleam` emit per-protocol Gleam source.

3. **Generated services** (`src/aws/services/...`) — emitted, no hand
   edits. DynamoDB is 20 kLOC, S3 is ~30 kLOC. Re-run via:
   ```
   gleam run -m aws_codegen -- awsJson1_0 .../dynamodb.json .../dynamodb.gleam
   gleam run -m aws_codegen -- restXml    .../s3.json       .../s3.gleam
   ```

## Wire-format verification

Smithy protocol compliance tests run via `gleam test`. Current pass /
fail counts (after the v0.1 close work):

| Protocol             | total | pass | fail | skip (no dispatcher) | skip (server-only) |
| -------------------- | ----- | ---- | ---- | -------------------- | ------------------ |
| awsJson1_0           |  75   |  51  |  0   |         18           |          6         |
| awsJson1_1           | 122   | 102  |  0   |         16           |          4         |
| restJson1            | 272   | 227  |  0   |         20           |         25         |
| restXml              | 197   | 174  |  0   |         15           |          6         |
| restXmlWithNamespace |   2   |   0  |  0   |          2           |          0         |
| awsQuery             |  77   |  41  |  0   |         36           |          0         |
| ec2Query             |  59   |  31  |  0   |         28           |          0         |
| rpcv2Cbor            |   4   |   0  |  0   |          4           |          0         |

`fail` is zero across every protocol. The `skip(no-dispatcher)` counts
mostly represent operations using `aws.protocols#httpChecksum` — the
multi-algorithm validation trait (S3 Get/PutObject and a few others)
that needs broader middleware than the simple Content-MD5 path,
deferred to v0.2. `smithy.api#httpChecksumRequired` is now supported:
the codegen appends a `Content-MD5: base64(md5(body))` step on
matching ops, verified end-to-end by the
`RestJsonHttpChecksumRequired` protocol-test case. The
`skip(server-only)` counts are response-side cases the test corpus
marks as `appliesTo: server`, which never affect SDK callers.

## Known gaps — most closed by the v0.1 close work

Items that were open at M6 cut-over and how they closed in the v0.1
close pass. The remaining ones are all explicit v0.2 candidates.

- **Response header binding — DONE.** Generated `parse_<op>_response`
  now emits `Output(..decoded, etag: rest.string_header(headers,
  "ETag"), ...)` overrides for every `@httpHeader` / `@httpResponseCode`
  output member. Full-override mode kicks in when an output has no
  body-bound members, sidestepping the "redundant record update"
  warning. (`aws/internal/codec/rest`.)
- **XML error-type extraction — DONE.** `runtime.extract_error_type`
  walks `<Code>...</Code>` (S3-style and `<ErrorResponse>` wrappers)
  after the JSON `__type` / `code` paths fall through. The header
  `x-amzn-errortype` still wins when present.
- **`@xmlFlattened` lists — DONE.** Codegen routes flattened list
  members through `xml_decode.optional_flat_list`. Default Smithy
  wrapping unchanged.
- **`@xmlName` on struct members — DONE.** The member-level
  `@xmlName` was always threaded into `MemberDef.json_name`; the
  decoder already used that as the element name, so closing the
  flattened-list gap closed this too. Verified end-to-end via
  `decode_list_buckets_output_xml` / `decode_list_objects_output_xml`.
- **Endpoint rules — DONE.** Per-service Smithy rule sets embed at
  codegen time (`smithy.rules#endpointRuleSet` trait, re-serialised
  back to JSON via `trait.to_json_string`). `runtime.invoke` walks
  the rule set per request, with `invoke_with_endpoint_params` for
  operation-specific parameters (S3 `Bucket` / `Key` etc.). Static
  `<prefix>.<region>` fallback retained for services without a rule
  set.
- **Streaming bodies — v0.2 gap.** `@streaming` blobs still skipped
  at the emitter level. `S3.GetObject` for v0.1 buffers the body to
  `BitArray`; a streaming HTTP send + receive path is on the v0.2
  list.
- **Paginators / waiters — v0.2 gap.** Not generated. Callers loop
  on `next_token` by hand against the typed outputs.
- **`smithy.api#httpChecksumRequired` — DONE.** The codegen now
  emits `let headers = rest.with_content_md5_header(headers, body)`
  on matching ops; `crypto.md5` + `rest.with_content_md5_header`
  ship the runtime side. Wire-format compliance asserted by
  `RestJsonHttpChecksumRequired` (one of the protocol-test cases
  that previously landed in `skip(no-dispatcher)`).
- **`aws.protocols#httpChecksum` — v0.2 gap.** The
  multi-algorithm request/response validation trait used by S3
  GetObject / PutObject is still emitter-skipped. Needs a broader
  middleware that picks the algorithm (sha256, crc32c, crc32,
  sha1) per request and validates response checksums.
